# Шаги бота и события

Состояние кода на 20.10.2026, после полной разметки событиями. Порядок — как шаги проходит родитель.

**Правило одно:** событие пишется каждый раз, когда шаг происходит. Уникальных людей считаем в SQL через `DISTINCT`, прохождения — по колонке `OfferEvent.attempt`. Дедупликации «раз на человека» больше нет.

Единственное исключение — `guide_sent`: гайд и по продукту отправляется один раз на человека.

**Как читать колонку «Событие»:**
- имя события — пишется в `OfferEvent`;
- **+№** — у события заполняется `questionNumber`;
- **нет** — события намеренно нет, причина указана.

Запросы воронки — в [analytics/funnel.sql](../analytics/funnel.sql).

## 2. Анкета

Три события на каждый вопрос, все с номером:

| Событие | Когда |
|---|---|
| `quiz_question_shown` **+№** | вопрос показан — при **каждом** показе |
| `quiz_question_answered` **+№** | ответ принят и сохранён |
| `quiz_answer_invalid` **+№** | ответ не принят: не число, текст вместо кнопки, не та кнопка |
| `quiz_out_of_range` **+№** | возраст вне 4–12 месяцев, анкета остановлена |

`quiz_question_shown` пишется из всех путей показа: переход к следующему вопросу, повтор после команды посреди анкеты, «Продолжить анкету» из напоминания, «Вернуться к анкете» из меню, прыжок админа командой `/goto`. Событие живёт внутри самой функции отправки вопроса, поэтому новый путь разметить не забудут.

Повторные показы отличаются в SQL: несколько `quiz_question_shown` с одним номером внутри одного `attempt`. Источник возврата виден по соседнему событию — `menu_back_to_quiz` или `quiz_reminder_continue_click`.

Показы внутри правки ответов сюда **не** попадают, у них свои события (раздел 3).

`quiz_q1` больше не пишется: его заменил `quiz_question_shown` с номером 1. Тип остался в enum ради записей до 20.10.2026, в воронке `/stats` шаг «Первый вопрос» считается по новому событию.

## 14. Начать заново

| № | Шаг | Событие |
|---|---|---|
| 14.1 | «Начать бот заново», `/restart`, а также `/start` посреди анкеты или пока готовится разбор | `restart_asked` |
| 14.2 | «Нет, вернуться» | `restart_cancelled` |
| 14.3 | «Да, начать заново» | `restart_confirmed` |
| 14.4 | То же, но ждавший разбор отменён | `restart_confirmed_cancelled_draft` |
| 14.5 | `/start` у того, кто анкету уже прошёл: новое прохождение заводится молча | `start_new_attempt` |

`/start` решает между 14.1 и 14.5 по тому, что человек теряет: идёт
анкета или ждёт разбор — спрашиваем, прохождение завершено — заводим
новое сразу. Если в прохождении ещё нет ни одного ответа, не делаем
ничего, кроме показа приветствия: заводить пустое прохождение незачем.
После подтверждения оба пути ведут на приветствие, а не на «Прежде чем
начать»; согласия, на которые ответ уже есть, пропускаются.

Оба подтверждения пишутся с **прежним** номером прохождения: событие закрывает старое прохождение, а не открывает новое. Номер передаётся явно, а не берётся из сессии, чтобы порядок строк в коде ничего не решал. Сразу после `Session.attempt` увеличивается, и дальше онбординг и анкета пишут события с новым номером.

## Что учитывать при работе с данными

**Прохождения считаются только по новым записям.** У событий до 20.10.2026 `attempt` равен `NULL`: по старым данным прохождения честно не различить. Все запросы воронки фильтруют `attempt IS NOT NULL`.

**Свои аккаунты исключаются в запросах, а не при записи.** Список в `INTERNAL_TELEGRAM_IDS`; тестирование идёт в боевом боте, и прохождения команды не должны портить статистику.

**Запись события не может сломать бота.** Всё внутри `logEvent` обёрнуто: упавшая запись уходит в лог, родитель получает ответ как обычно.
